# 资源配额申请流程

## 1. 文档目的

本流程说明如何在算力集群申请计算资源、存储配额和 GPU 时间，帮助用户快速获取所需资源。

## 2. 配额类型

### 2.1 计算资源配额

| 资源类型 | 单位 | 默认配额 | 最高配额 | 申请门槛 |
|----------|------|----------|----------|----------|
| GPU 卡时 | 卡·小时/月 | 1,000 | 50,000 | - |
| GPU 数量 | 张 | 8 | 512 | 项目立项 |
| CPU 核时 | 核·小时/月 | 10,000 | 500,000 | - |
| 内存配额 | GB | 256 | 32,000 | - |
| 并发作业数 | 个 | 5 | 50 | 项目立项 |

### 2.2 存储资源配额

| 存储类型 | 默认配额 | 最高配额 | 用途说明 |
|----------|----------|----------|----------|
| /data | 10 TB | 500 TB | 训练数据集 |
| /checkpoint | 5 TB | 100 TB | 模型检查点 |
| /scratch | 2 TB | 20 TB | 临时计算 |
| /project | 20 TB | 200 TB | 项目共享 |

### 2.3 特殊资源

| 资源类型 | 申请要求 | 审批级别 | 特殊说明 |
|----------|----------|----------|----------|
| 高优先级队列 | 项目立项 | 部门负责人 | 最多占用 20% |
| 超长时间作业 | 72h+ | 运维负责人 | 最长 336h |
| 大规模节点 | 64+ 节点 | 技术委员会 | 需提前 2 周 |
| 特殊 GPU 型号 | H100 专用 | 采购审批 | 按需分配 |

## 3. 申请入口

### 3.1 线上申请系统

**Portal 地址：** https://cluster.company.com/portal

**操作流程：**
1. 登录 Portal (企业 SSO)
2. 进入「资源管理」→「配额申请」
3. 选择资源类型并填写申请
4. 提交审批流程

### 3.2 API 接口

```bash
# REST API 申请配额
curl -X POST https://cluster-api.company.com/v1/quota/request \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{
    "resource_type": "gpu_hours",
    "quantity": 10000,
    "period": "monthly",
    "project_id": "project_alpha",
    "justification": "大模型预训练需求"
  }'
```

## 4. 审批流程

### 4.1 标准审批流程

```
申请人提交申请
    ↓
系统自动初审 (1 小时内)
    ↓
┌─────────────────────────────────┐
│ 资源规模判断：                    │
│ 小规模 (< 100 卡时/月):           │
│   → 运维自动审批                  │
│ 中规模 (100-1000 卡时/月):        │
│   → 项目负责人审批                 │
│ 大规模 (> 1000 卡时/月):         │
│   → 部门负责人审批                 │
│ 超大规模 (> 5000 卡时/月):        │
│   → 技术委员会审批                 │
└─────────────────────────────────┘
    ↓
审批完成 (SLA 内)
    ↓
资源配额生效
```

### 4.2 审批 SLA

| 申请类型 | 自动审批 | 人工审批 | 最长响应 |
|----------|----------|----------|----------|
| 常规配额 | 1 小时内 | 2 工作日 | 3 工作日 |
| 配额调整 | 2 小时内 | 1 工作日 | 2 工作日 |
| 紧急扩容 | 30 分钟 | 4 小时 | 24 小时 |
| 新项目立项 | - | 5 工作日 | 1 周 |

### 4.3 审批权重因素

| 因素 | 权重 | 说明 |
|------|------|------|
| 项目优先级 | 30% | P0-P3 项目等级 |
| 历史使用率 | 25% | 配额利用率 |
| 资源可用性 | 20% | 集群剩余容量 |
| 业务重要性 | 15% | 对公司业务价值 |
| 申请合理性 | 10% | 申请与实际需求匹配 |

## 5. 紧急扩容流程

### 5.1 适用场景

以下情况可触发紧急扩容：
- 生产环境 GPU 故障导致任务堆积
- 业务紧急需求（如客户交付）
- 算力瓶颈影响业务 SLA

### 5.2 紧急扩容申请

```yaml
# 紧急扩容申请模板
urgent_request:
  type: emergency_expansion
  priority: P1
  reason: |
    客户演示需要，24小时内完成模型训练
  
  requested_resources:
    gpu_hours: 500
    duration: 24h
    
  approval_chain:
    - name: 运维值班
      contact: ops-oncall@company.com
      sla: 30 分钟响应
      
    - name: 部门负责人
      sla: 2 小时审批
```

### 5.3 紧急响应流程

```
紧急扩容请求 (P1)
    ↓
运维值班 30 分钟内响应
    ↓
评估资源可用性
    ↓
┌────────────────────────────────┐
│ 有可用资源：                     │
│ → 临时配额释放                  │
│ → 4 小时内生效                  │
└────────────────────────────────┘
    ↓
┌────────────────────────────────┐
│ 需采购/调度：                   │
│ → 触发临时资源池               │
│ → 通知资源协调                 │
│ → 24 小时内提供方案            │
└────────────────────────────────┘
    ↓
使用完毕后恢复标准配额
```

### 6.2 告警阈值配置

| 资源类型 | 预警阈值 | 告警阈值 | 紧急阈值 |
|----------|----------|----------|----------|
| GPU 卡时 | 70% | 85% | 95% |
| 存储空间 | 75% | 90% | 95% |
| 并发作业 | 80% | 90% | 100% |

### 6.3 告警通知

| 通知级别 | 触发条件 | 通知方式 | 接收人 |
|----------|----------|----------|--------|
| INFO | 使用 > 50% | 邮件 | 用户 |
| WARNING | 使用 > 70% | 邮件 + 短信 | 用户 + 负责人 |
| CRITICAL | 使用 > 85% | 邮件 + 短信 + 电话 | 用户 + 负责人 + 运维 |
| EXCEEDED | 超过配额 | 阻断提交 | 用户 |

### 6.4 配额释放机制

| 机制 | 说明 | 触发条件 |
|------|------|----------|
| 自动释放 | 未使用资源自动回收 | 作业结束后 24h 未使用 |
| 定期清理 | 过期数据删除 | /scratch 7 天未访问 |
| 强制回收 | 恶意占用处理 | 违规使用调查后 |
| 临时展期 | 紧急情况延期 | 审批通过后 |

## 7. 配额调整

### 7.1 调整申请条件

以下情况可申请配额调整：
1. 项目规模扩大，需要更多资源
2. 原有估算不足，需增加配额
3. 业务优先级提升，需更高优先级
4. 资源利用率持续 > 90%

### 7.2 调整流程

```
调整申请入口：Portal → 资源管理 → 配额调整

申请表单内容：
├── 当前配额信息
├── 申请调整原因
├── 预期使用计划
├── 历史使用数据分析
└── 预期收益/价值

审批流程：与新申请相同
```

### 7.3 配额退还

如项目完成或资源闲置，可申请退还配额：
```yaml
# 配额退还申请
return_request:
  user: alice
  project: project_alpha
  resources:
    gpu_hours: 2000  # 退还 2000 卡时
    storage_data: 5TB  # 退还 5TB 存储
  reason: 项目已结项，资源释放
```

## 8. 常见问题

### 8.1 FAQ

| 问题 | 解答 |
|------|------|
| 申请被拒怎么办？ | 查看拒绝原因，可申诉或调整后重新申请 |
| 配额不足时作业会怎样？ | 作业排队等待，直到有可用配额 |
| 可以跨项目使用配额吗？ | 原则上不可以，需项目间资源协调 |
| 配额多久重置？ | GPU 卡时/月为周期重置，存储配额不重置 |
| 紧急情况联系谁？ | 运维值班：ops-oncall@company.com |

### 8.2 资源协调联系方式

| 需求 | 联系部门 | 联系邮箱 |
|------|----------|----------|
| 常规申请 | 运维支持 | ops-support@company.com |
| 紧急扩容 | 运维值班 | ops-oncall@company.com |
| 新项目立项 | 资源委员会 | resource-committee@company.com |
| 长期资源规划 | 基础设施 | infra-team@company.com |

## 9. 资源使用规范

### 9.1 合规使用要求

- 资源仅用于申请时申报的用途
- 禁止转租或转让配额
- 禁止利用资源进行商业挖矿
- 禁止长期占用不使用资源
- 敏感数据处理需遵守安全规范

### 9.2 违规处理

| 违规行为 | 第一次 | 第二次 | 第三次 |
|----------|--------|--------|--------|
| 资源滥用 | 警告 | 暂停配额 1 周 | 收回配额 |
| 闲置资源 | 自动回收 | 警告 | 收回配额 |
| 违规用途 | 立即停用 | 收回配额 | 永久禁止 |
| 安全违规 | 立即停用 + 审计 | - | - |
